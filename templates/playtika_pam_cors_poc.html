Playtika Octopus Ad Manager (PAM) — CORS PoC

This page demonstrates the reflective Access-Control-Allow-Origin + Access-Control-Allow-Credentials: true misconfiguration on octopus.playtika.com and octopus-events.playtika.com. It is the read-only PoC linked from H1 report "Playtika Octopus Ad Manager — Reflective CORS with Credentials on Every Endpoint of an Internal Admin SPA".

Safety boundary (please read)

This PoC is intentionally read-only. It issues:

  • OPTIONS preflight requests to introspect what the CORS layer permits (no state effect).
  • One GET /api/json/everything with credentials: include to demonstrate the credentialed read primitive.

It does NOT issue any POST, PUT, PATCH, or DELETE against PAM. The preflight evidence below plus the source-code analysis in the H1 report (zero CSRF tokens in 100+ extracted JS files, cookie-only auth) are sufficient to demonstrate the write primitives without us creating admin users or modifying ad-auction config on a production ad-monetization platform.

If your browser blocks the credentialed read (e.g. because the PAM session cookie is SameSite=Lax or Strict), the application-layer chain is dead in modern browsers and the bug is limited to a CORS-layer misconfig. The PoC tests both possibilities and reports the result.

Prerequisite for the read test

Open https://octopus.playtika.com/ in this same browser, complete the Microsoft Entra OAuth login, then return here. (For Test 1, no PAM session is needed — it only inspects CORS preflight responses.)

Test 1: GET preflight from this origin

Issues OPTIONS /api/json/everything with Origin: https://jakegarnier.com + Access-Control-Request-Method: GET. A correctly-configured server should refuse or omit the credentials header. A vulnerable server reflects the attacker origin and sends Access-Control-Allow-Credentials: true.







  
Test 2: Same misconfiguration on octopus-events.playtika.com

  
Sends the same preflight to the twin host to demonstrate the issue is not isolated to a single deployment.

  
  






  
Test 3: POST / PUT / DELETE preflights for state-changing endpoints

  
Sends preflight OPTIONS for POST /api/json/addUser, PUT /api/json/updateUser, and DELETE /api/json/addUser. We do not issue the actual state-changing requests — the preflight result alone proves the CORS layer would permit them.

  
  






  
Test 4: Credentialed cross-origin GET /api/json/everything

  
This is the only test that issues a credentialed request. The fetch uses credentials: 'include' so the browser auto-attaches your PAM session cookie if its SameSite attribute permits cross-origin attachment. Three outcomes are possible:

  
    
    
  1. You are not logged into PAM → response is 401 Not signed in with the bad CORS headers. Proves the CORS layer is permissive but not that your data leaked.
    2. 
    
  2. Logged in AND SameSite permits → response is the full admin data set. This is the primary impact the H1 report claims.
    3. 
    
  3. Logged in but SameSite=Lax/Strict → the cookie is not attached, response is 401, indistinguishable from outcome (1). This is the gating condition we could not validate without an authenticated test session.
    4. 
  

  
The response body is displayed in-page only — nothing is sent to any external server. Body output is truncated to the first 8 KB to keep the page readable; if you need the full response, open browser DevTools and inspect the Network panel.
